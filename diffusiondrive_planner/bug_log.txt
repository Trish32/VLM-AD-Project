[2026-08-16] BLOCKER 2 — deformable_aggregation_ext (custom CUDA kernel)
------------------------------------------------------------------------
Fingerprint: ModuleNotFoundError: No module named 'deformable_aggregation_ext'

Cause: SparseDrive's Deformable Aggregation is a hand-written CUDA kernel
(ops/src/deformable_aggregation_cuda.cu). Cannot build on Apple Silicon.

Fix: diffusiondrive_planner/dfa_torch.py — pure-PyTorch equivalent, wired in via
ops/__init__.py when HAS_DFA_EXT is False. Calls the torch version directly rather
than upstream's autograd.Function (whose backward also lives in the extension), and
lets autograd differentiate through grid_sample.

Kernel semantics recovered by reading the .cu (all four were load-bearing):
  1. Thread index decomposes [batch, anchor, pts, cam, scale, embed], embed fastest;
     output accumulates over (pts, cam, scale) via atomicAdd.
  2. sampling_location has NO scale axis (same loc reused at every scale) and is
     stored (w, h) — NOT (h, w).
  3. Points are DROPPED, not clamped: `if (loc_w <= 0 || loc_w >= 1) return;`.
     Strict inequality — a point exactly on the border contributes nothing.
  4. Groups are CONTIGUOUS channel blocks: group = channel // (num_embeds//num_groups).
     => repeat_interleave, not repeat. Using repeat keeps every shape valid while
     scrambling which weight hits which channel.
  5. `h_im = loc_h*H - 0.5` is exactly grid_sample(align_corners=False) under
     grid = 2*loc - 1; the kernel's per-corner bounds checks are padding_mode='zeros'.

Verification: tests/test_dfa_torch.py diffs the vectorized grid_sample version against
`dfa_naive`, an independent literal transcription of the kernel (explicit floor,
explicit corner bounds checks). The two share no code and reason in different spaces
(normalized [-1,1] vs raw pixel offsets), so a wrong mapping makes them disagree.
Agreement to 1e-10 in float64 across 3 seeds incl. border/outside/exactly-0/exactly-1.
8 passed, 1 skipped.

VERIFIED against the real CUDA kernel 2026-08-16 on a Kaggle Tesla T4 (torch 2.10.0+cu128)
via tools/validate_dfa_cuda.py — a self-contained bundle JIT-built with
cpp_extension.load, no GCP credits spent:

  case                     max abs diff   max rel diff   verdict
  tiny seed=0                 9.537e-07      4.966e-06   PASS
  tiny seed=1                 7.153e-07      1.729e-05   PASS
  tiny seed=2                 9.537e-07      2.807e-06   PASS
  realistic 900x13x256        4.578e-05      1.246e-01   PASS

All within float32 tolerance on ABSOLUTE error, including the realistic shape regime the
model actually runs in.

The realistic case's large max RELATIVE error (12.5% on run 1, 36.4% on run 2) was checked
with a diagnose() pass and is CONFIRMED HARMLESS — accumulation order, not structure:

  realistic 900x13x256:
    worst-rel element |want| = 7.033e-06   (err 2.563e-06)
    median |want|            = 7.816e+00   -> the culprit is ~6 orders below typical
    max rel on |want|>median = 2.125e-06   <- pure float32 rounding
    frac of elements rel>1%  = 0.00%       (0 of 230,400)

Cause: the CUDA kernel accumulates via atomicAdd in NONDETERMINISTIC order across
cam x scale x pts; the torch version sums in fixed loop order, so float32 rounding differs.
That inflates the RATIO only where the true value is ~0.

Independent corroboration: max rel error CHANGED between two runs (0.125 -> 0.364) while
every absolute figure stayed identical — exactly what nondeterministic atomicAdd predicts,
and impossible for a structural mismatch, which would be deterministic.

LESSON: on a reduction validated against a CUDA kernel, judge by ABSOLUTE error plus
relative error restricted to elements above the median magnitude. Raw max-relative error is
meaningless near zero and will scare you off a correct implementation.

Portability fix the bundle must apply: upstream's .cu includes <THC/THCAtomics.cuh>,
removed in torch 1.11. The generator rewrites it to <ATen/cuda/Atomic.cuh>, without which
it will not compile on any modern Colab/Kaggle image.

[2026-08-16] BUG 4 — DDIM clip_sample ordering (found by diffing vs diffusers)
------------------------------------------------------------------------------
Fingerprint: our TruncatedDDIM.step matched diffusers at t=0 but diverged for all t>0.
Max abs diff ~1.9 on random inputs — far too large for precision.

Two distinct causes, found in order:

(a) alphas_cumprod built in float64 then cast; diffusers builds it in float32.
    Symptom: ~2e-6 disagreement everywhere. Fix: build betas in float32 too.
    LESSON: match the reference's precision, not the mathematically better one.

(b) THE REAL BUG. diffusers' DDIMScheduler.step derives pred_epsilon from the
    UNCLIPPED pred_original_sample, and only clips x0 AFTERWARDS:
        pred_original_sample = model_output
        pred_epsilon = (sample - a**0.5 * pred_original_sample) / b**0.5
        ... elif clip_sample: pred_original_sample = clamp(...)
    We clipped first, then derived epsilon. Clipping first is the natural reading.
    (use_clipped_model_output defaults False, so epsilon is never recomputed.)

Also note clip_sample=True / clip_sample_range=1.0 are diffusers DEFAULTS that upstream
never overrides — invisible at the call site. Nearly a no-op in upstream's pipeline
because they normalize x_start into [-1,1] first, which is exactly why it would have
survived unnoticed into the checkpoint comparison.

Result: 21/21 tests pass, exact agreement with DDIMScheduler on add_noise, step, and
the full 2-step inference loop.

[2026-08-16] FINDING 6 — planning frame is x=LATERAL (right +), y=FORWARD

threshold, and confirmed empirically on mini: mean |x_final| 0.99m vs |y_final| 16.55m,
y>0 in 90.4% of samples. gen_plan_anchors.py ASSERTS this rather than assuming it — a

[2026-09-11] DEMO VIDEO RENDERER — four frame/format traps
-----------------------------------------------------------
tools/make_demo_video.py renders the mini_val cache (no model re-run) into a video in the
shape of upstream's final_github.mp4. Four things had to be pinned down first; each was
found by checking against data rather than by reading, and each would have produced a
plausible-looking but wrong video.

1. THE PLAN FRAME IS x=RIGHT, y=FORWARD — and BOTH conventions appear in one sample.
   Probed by projecting unit axes through `lidar2img`: (0,10,0) lands at u=841 in
   CAM_FRONT (image is 1600 wide, so dead centre) and (0,-10,0) lands in CAM_BACK.
   So index 1 is forward, index 0 is lateral, +x to the right. `_render_sdc_car`'s
   `extent=(-1,1,-2,2)` independently agrees: the ego is 2 m wide in x, 4 m long in y.

2. `result['planning']` and `final_planning` ARE ABSOLUTE WAYPOINTS, but
   `gt_ego_fut_trajs` ARE PER-STEP DELTAS.
   The head cumsums before it stores, so `planning[cmd, best] == final_planning` exactly.
   Upstream's own `draw_planning_pred` prepends the origin WITHOUT a cumsum, while
   `draw_planning_gt` cumsums — the asymmetry is real, not a bug in their code. Applying
   cumsum to the prediction (the natural reading, and what the commented-out code in
   cam_render.py does) turns a 12 m plan into a 42 m one and still looks like a
   trajectory.

3. GROUND PLANE: use the EXTRINSICS, not the detections.  <-- cost a real debug cycle
   First cut estimated it as median(box_z - h/2) over confident detections. On
   scene-0916 that gives -1.72 and the re-projected corridor lands on the road; on
   scene-0103 frame 15 it gives -2.28 and the corridor projects to v=959..1926 on a
   900-px-tall image, i.e. entirely below the frame. It rendered as "the overlay is
   missing" with no error.
   Cause: box-bottom spread inside ONE frame is over 2 m (p25 -2.10, p75 -1.33 across
   mini_val), so the median is not a ground estimate at all.
   Fix: `lidar2ego_translation[2]` = 1.84019. nuScenes puts the ego frame origin on the
   ground at the rear-axle midpoint, so the LiDAR z offset IS its height above the road.
   Cross-check: GT box bottoms have median -1.626 across all 81 samples, ~21 cm above
   -1.840, which is what real terrain plus box-fitting slack should look like.

4. L2 IS THE MEAN OVER THE HORIZON, NOT THE ENDPOINT ERROR.
   The on-screen metric first showed |plan[-1] - gt[-1]|, which reads 2.04 m on mini_val
   against a published 0.96 m at 3 s. Both numbers are "L2 at 3s" in plain English.
   Upstream's PlanningMetric averages the per-step displacement over every 0.5 s step up
   to the horizon. Recomputing that way reproduces the eval run exactly:
     ours 0.2434 / 0.5492 / 0.9604  vs  eval_planning.py 0.2433 / 0.5490 / 0.9603.
   Also kept upstream's sample gate (`if not sdc_planning_mask.all(): continue`), so the
   last keyframes of a scene are left unscored rather than scored on a short horizon —
   scoring them shifted 1s/2s to 0.1446/0.3202 on scene-0916, i.e. a different metric.

   Per-scene, with the correct definition:
     scene-0916  L2  0.145 / 0.323 / 0.560 m   (n=35)   parking lot, both turns
     scene-0103  L2  0.343 / 0.780 / 1.371 m   (n=34)   decelerates to ~1.8 m/s
     mini_val    L2  0.243 / 0.549 / 0.960 m   (n=69)
   scene-0103 carries nearly all the error: the planner under-predicts the hard brake
   for the turning car, which the L2 trace in the video shows as a spike to ~4 m.

NOT A BUG, documented in tests/test_demo_control.py: pure-pursuit curvature reads 3.3-3.7%
high on a constant-curvature arc, consistently across radii 12-100 m. A plan is 6
waypoints 0.5 s apart and linear interpolation between them puts the lookahead point on a
chord, which for a convex path lies further off the centreline than the arc. A real
controller reading these waypoints sees the same bias, so the test asserts its magnitude
and sign instead of tuning it away.
